# Hotspot Pulse 网站上线重规划

更新日期：2026-05-13

## 目标

先把 Hotspot Pulse 作为一个可稳定访问、可人工运营的 MVP 上线，再逐步增强数据源、历史数据、账号权限和日报分发能力。

上线首版不追求一次性完成所有产品设想，核心目标是：

- 用户可以通过正式域名访问热点看板和日报页。
- 管理员可以登录后台、刷新热点、编辑日报、推送企业微信。
- 数据采集失败时页面仍可展示最近一次快照，不出现空白站点。
- 密钥、管理员密码、Webhook 不进入代码仓库。
- 上线后有基础日志、重启策略和备份方案。

## 当前判断

项目当前适合用 Node.js 单服务上线：

- 启动命令：`npm start`
- 服务入口：`src/server.js`
- 默认端口：`4173`
- 前端静态文件：`public/`
- 当前持久化：`data/trends.json`、`data/daily.json`、`data/manual-links.json`
- 主要接口：热点列表、手动刷新、管理员登录、日报保存、企业微信推送

首版可以不引入复杂前后端拆分，先使用一台云服务器或轻量 PaaS 托管 Node 服务。

## 推荐上线方案

### 阶段 1：上线前冻结范围

建议冻结首版范围为：

- 首页热点聚合看板
- 日报公开页
- 管理员登录
- 手动添加热点链接
- 保存日报
- 企业微信推送日报链接
- 自动定时刷新热点

暂缓到第二阶段：

- 多用户账号体系
- PostgreSQL 历史趋势库
- AI 摘要
- 收藏、日报归档、订阅
- 复杂权限和审计后台

### 阶段 2：部署环境

推荐优先级：

1. 云服务器 + Node.js + 反向代理
2. Render、Railway、Fly.io 等 Node PaaS
3. Vercel 仅托管前端，后端另放云服务

由于当前项目会写入本地 `data/*.json`，不建议首版直接放到无持久磁盘的 Serverless 环境。

服务器最低配置建议：

- Node.js 20 或更新版本
- 1 核 CPU
- 1 GB 内存
- 10 GB 磁盘
- HTTPS 域名
- 进程守护，例如 PM2、systemd 或平台自带健康重启

### 阶段 3：上线配置

生产环境需要配置：

```text
PORT=4173
REFRESH_INTERVAL_MINUTES=30
ADMIN_PASSWORD=强密码
PUBLIC_DAILY_URL=https://你的域名/daily.html
WECOM_BOT_WEBHOOK=企业微信机器人 webhook
```

数据源配置建议：

```text
X_SOURCE=trends24
WEIBO_SOURCE=official-first
TIKTOK_SOURCE=creative-center
REDDIT_SOURCE=proxy-first
```

如果微博、TikTok、Reddit 在服务器网络中不稳定，需要优先替换为更稳定、合规的数据供应方式。

### 阶段 4：上线检查清单

上线前必须检查：

- `.env` 不提交到代码仓库。
- `ADMIN_PASSWORD` 已改成强密码。
- `PUBLIC_DAILY_URL` 已改为正式域名。
- 企业微信推送使用正式 Webhook。
- 服务启动后访问 `/` 正常。
- 访问 `/daily.html` 正常。
- 管理员登录成功。
- 手动刷新热点成功。
- 保存日报后，公开日报页内容同步更新。
- 企业微信能收到日报链接。
- 重启服务后，日报和热点快照仍然存在。

### 阶段 5：首版上线流程

建议按这个顺序执行：

1. 准备服务器或 PaaS 项目。
2. 安装 Node.js 20+。
3. 拉取项目代码。
4. 配置生产 `.env`。
5. 启动服务并验证本机端口。
6. 配置域名和 HTTPS。
7. 配置进程守护和自动重启。
8. 手动触发一次热点刷新。
9. 选择 5-10 条热点保存日报。
10. 推送企业微信测试消息。
11. 开放正式访问。

## 7 天上线排期

### 第 1 天：确认首版范围

- 冻结 MVP 功能。
- 确认正式域名。
- 确认部署平台。
- 确认管理员和企业微信接收群。

### 第 2 天：生产环境部署

- 配置 Node 运行环境。
- 配置 `.env`。
- 跑通正式环境服务。
- 配置 HTTPS。

### 第 3 天：数据源稳定性测试

- 连续刷新 5 次观察失败平台。
- 记录每个平台的可用状态。
- 对不稳定数据源设置降级策略或替代源。

### 第 4 天：运营流程测试

- 管理员登录。
- 手动添加链接。
- 选择热点生成日报。
- 推送到企业微信。
- 验证移动端展示。

### 第 5 天：可靠性补强

- 配置服务自动重启。
- 配置日志留存。
- 配置 `data/` 目录备份。
- 添加基础健康检查访问路径或监控探测。

### 第 6 天：小范围试运行

- 邀请内部用户访问。
- 收集页面加载、热点质量、日报可读性反馈。
- 修正文案、默认排序和明显样式问题。

### 第 7 天：正式上线

- 更新正式入口。
- 固定每日运营时间。
- 每日生成并推送日报。
- 记录上线后问题清单，进入第二阶段迭代。

## 上线后的第二阶段

优先级从高到低：

1. 将 `data/*.json` 迁移到 PostgreSQL，保留历史趋势。
2. 增加健康检查、错误告警和采集失败统计。
3. 为数据源增加更明确的状态展示。
4. 增加日报归档页。
5. 增加 AI 摘要和标题聚类优化。
6. 增加用户登录、收藏和订阅。

## 风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 公共数据源变动 | 热点刷新失败 | 保留最近快照，准备备用数据源 |
| 本地 JSON 存储丢失 | 日报和热点快照丢失 | 定时备份 `data/`，第二阶段迁移数据库 |
| 管理员密码泄露 | 后台被操作 | 使用强密码，后续增加账号体系 |
| Serverless 无持久磁盘 | 数据无法保存 | 首版使用带持久磁盘的部署方式 |
| 企业微信 Webhook 失效 | 日报无法推送 | 上线前实测，失败时保留公开日报链接 |

## 首版验收标准

上线完成后，满足以下条件即可认为首版可发布：

- 正式域名可访问首页。
- 正式域名可访问日报页。
- 管理员可以完成登录、刷新、保存、推送完整流程。
- 页面刷新后不会丢失当前日报。
- 服务重启后仍能读取最近热点快照。
- 连续运行 24 小时无进程退出。
- 数据源失败时，页面有可用的历史内容。
